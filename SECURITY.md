# Security and update policy

- **Isolation:** Rootless Podman, no host sockets/home mounts, capability drop and `no-new-privileges`. `usb` exposes one device; `nested` relaxes seccomp. Networking is enabled and may reach the LAN. A VM is safer for high-risk programs.
- **Base:** `docker.io/opensuse/tumbleweed:latest` (tested rolling snapshot); fresh uncached builds execute `zypper refresh` and `zypper dup --no-recommends` before installing the RPM toolchain. On amd64, refresh includes the `shells:fish` OBS repository; arm64 uses only the image's default repos. Tumbleweed does not provide the patch metadata needed for a reliable `zypper patch-check` security gate. Snapshot transitions can cause build failures. Watch advisories and build logs.
- **Preinstalled toolchains:** All profiles include the core Node.js, Python, Rust and Go CLI toolchains plus basic compilers from Tumbleweed's standard repositories. The fish shell uses the `shells:fish` OBS repo on x86_64 (minimum 4.9.3), but stock Tumbleweed on aarch64 because OBS does not currently publish the matching package. The initial x86_64 Zypper refresh automatically imports the OBS-provided signing key; this checks signatures but does not pin the key's fingerprint. A changed repository key therefore warrants independent review. This increases image size and attack surface compared with a minimal base. The shared package list is in `scripts/install-cli-toolchain.sh`; additions are subject to the same Trivy gate. No language-registry install scripts execute at build time.
- **Cadence:** The GHCR workflow runs approximately every three days, plus pushes and manual runs. GitHub cron uses days 1, 4, 7, ... of each month, not a guaranteed 72-hour cadence; scheduled jobs may be delayed or suspended for inactivity.
- **Gate:** Tumbleweed's `zypper dup` is performed before package installation; Zypper refresh, upgrade and installation failures stop the build. Trivy supports openSUSE Tumbleweed OS advisories and scans candidate digests on amd64 and arm64. Any scanner error or **fixable HIGH/CRITICAL** CVE blocks `latest`/version tag promotion. This is not equivalent to Fedora's DNF advisory query or a complete CVE inventory. **Unfixed** vulnerabilities can remain; false negatives are possible. Failed runs retain the previous published image. The unique candidate tag can remain accessible in a public package.
- **Traceability:** The workflow creates Buildx multi-arch SBOM metadata, two SPDX JSON SBOM artifacts, GitHub provenance and SBOM attestations, and a Cosign keyless signature on the multi-arch image digest. Verify signatures against the repository's *specific workflow identity*, not only the registry address.
- **Rollout:** GHCR does not automatically patch running Podman containers. Pull the new image and recreate each container; retain your named `/work` volume as needed. Production users should pin a verified digest and update it deliberately.
- **Operational controls:** Protect workflow changes and release tags with appropriate GitHub repository permissions. If `GITHUB_TOKEN` lacks package write permission, grant the repository permission on existing GHCR packages. GitHub Artifact Attestations in private repos require eligible GitHub plans.
- **Reporting:** Use GitHub's private vulnerability reporting feature, when enabled, or contact the maintainer privately. Keep the openSUSE and RPM notices intact; see `THIRD_PARTY_NOTICES.md`.
